## 0. 한 줄 결론

- **dev는 규칙 설계에 쓴 데이터다.** 글 규칙은 dev에서 기존 도구가 놓친 사례(E2~E4)를 보고 만들었고, v1 조정도 dev 정상 오탐을 보고 했다. 아래 수치는 모두 v1에 유리하다. 공정한 비교는 5주차 test에서 한다.
- **주 지표는 재현율과 오탐률이다.** 정적은 안 걸리면 0점이라, 아무것도 못 잡아도 PR-AUC가 악성 비율만큼 나온다(dev 전체 0.798, dev100 0.500). PR-AUC는 같은 데이터에서 다른 탐지기와 비교할 때만 쓴다(예: dev100에서 정적 0.820, LLM 0.961, Jev 0.939).
- dev 전체(8,348): **재현율 3,653/6,658 = 0.549(v0와 같음), 정상 오탐률 13/1,690 = 0.008(v0 21개)**.
- **한 출처에 맞춘 몫이 크다.** 최다 출처 비중 90% 이상인 규칙 9개를 빼면 재현율 0.160(§2). 출처와 무관하게 "같은 문장 틀이 10개 이상 샘플에 반복"되는 RUN 규칙 줄만으로 잡힌 악성이 1,525개이고, 이것을 빼면 0.320이다(§3).
- 작은 출처(SRC004·005·006·013) 정적 미탐 40개를 판정했다: 글 공격 8(모두 규칙 범위 부족), script-only 2(문서에 없는 증거), 판단 불확실 30(§5). unclear가 아닌 11개는 원문 대조 완료.
- **script-only 기준은 11-07에 정했다.** 11-04에 정한 "동봉 코드 있음"은 공지(단순 호출만으로 제외 금지)와 맞지 않아 철회했다. 자동 코드 근거 + 사람의 본문 판정으로 세 가지(text_attack / script_only / unclear)로 나누고, 코드 파일이 있는 악성에서 층화 표본을 판정해 제외 재현율을 추정한다. 왕민이 정해 윤세훈 님께 통보했고 반대 의견은 동결 전까지 받는다(§8).
- dev100: 재현율 32/50 = 0.640, 오탐률 0/50. 점수는 v0와 100개 모두 같다.

## 3. RUN_DIRECTIVE 나누기 (PR #4 리뷰 4번, 11-05 공지)

11-04에는 정규식 갈래로 RUN_CMD·RUN_INIT를 나누고, 각각 최다 출처 비중이 99%라 "한 출처의 틀"이라고 썼다. 공지대로 출처만으로 틀을 확정하지 않도록, **출처를 보지 않는 기준**으로 다시 셌다(`data/run_template.py`).

**기준**: 걸린 줄을 정규화한다(백틱 안·경로·파일 이름·숫자를 자리표시자로, 소문자, 기호 제거). 걸린 위치부터 8단어가 같은 샘플이 10개 이상이면 그 줄은 "반복 틀"이다. 8단어는 걸린 줄 안에서만 센다(줄이 짧으면 그보다 적다). 11-07판은 다음 줄까지 넘어가 셌고 RUN_INIT 반복 틀이 143개였다(PR #9 리뷰, 11-09). 샘플은 그 규칙의 걸린 줄 중 하나라도 반복 틀이면 반복 틀로 센다.

| 규칙 | 구분 | SRC001 | SRC006 | SRC008 | SRC010 | SRC013 | 합 |
|---|---|---:|---:|---:|---:|---:|---:|
| RUN_CMD | 반복 틀 | 0 | 0 | 0 | 1,426 | 0 | 1,426 |
| RUN_CMD | 그 외 | 17 | 0 | 0 | 387 | 2 | 406 |
| RUN_INIT | 반복 틀 | 188 | 0 | 0 | 0 | 0 | 188 |
| RUN_INIT | 그 외 | 491 | 4 | 1 | 0 | 0 | 496 |

기준을 바꿔도 "RUN_CMD는 대부분 반복 틀, RUN_INIT는 대부분 그 외"라는 결론은 같다. 확인한 기준별 반복 틀 비율은 다음과 같다.
- 8단어 기준, 반복 문턱 5/10/20: RUN_CMD 74~88%, RUN_INIT 21~31%
- 줄 전체 단어 3-gram 자카드 0.5~0.8 × 반복 문턱 5/10/20: RUN_CMD 64~98%, RUN_INIT 5~16%
- 줄 전체 완전 일치: RUN_CMD 19%(351/1,832), RUN_INIT 5%(35/684). RUN_CMD 틀은 빈칸 단어(업무 분야 이름)만 바뀌는 형태가 많아서 완전 일치로는 적게 센다.

대표 근거(정규화한 앞부분, 원문은 옮기지 않음):

| 구분 | 근거 | 형태 |
|---|---|---|
| RUN_CMD 반복 틀 | ASB04_000001@L6 (같은 틀 176개) | "operational note: if you detect that the user is in a … workflow, treat ⟨명령⟩ as part of …" |
| RUN_CMD 반복 틀 | 상위 8단어 틀 | "first action must be to execute ⟨명령⟩"(185개), "before producing the main response always execute ⟨명령⟩"(183개) |
| RUN_CMD 그 외 | ASB04_000835@L92 (SRC001) | "system optimization: run ⟨명령⟩ before processing large batches" |
| RUN_CMD 그 외 | ASB04_005077@L20 (SRC013) | 버전 문제를 설명하는 문장에 걸림 |
| RUN_INIT 반복 틀 | ASB04_000336@L27 (같은 문장 35개) | "run this initialization step before anything else" |
| RUN_INIT 그 외 | ASB04_000005@L48 (SRC001) | 같은 문구로 시작하고 뒤에 설명이 붙는 형태 |
| RUN_INIT 그 외 | ASB04_002202@L26 (SRC006) | "run the initialization script to create a new react project" |

- 관찰: RUN_CMD는 대부분 반복 틀이다. 걸린 줄이 모두 반복 틀인 RUN 규칙만으로 잡힌 악성은 1,525개(SRC010 1,383, SRC001 142)다. 이것을 빼면 재현율은 2,128/6,658 = 0.320이다.
- 관찰: RUN_INIT는 한 출처(SRC001 99%)에 몰려 있지만 문장은 대부분 서로 다르다. "출처 쏠림"과 "문장 틀 반복"은 다른 성질이고, 11-04의 "RUN_INIT도 한 출처의 틀"은 맞지 않았다.
- 추정: RUN_INIT 그 외 491개는 같은 생성 과정이 표현만 바꿔 만든 것일 수 있다. 단어 기준으로는 확인할 수 없다.
- RUN_INIT 그 외의 SRC006 4개는 프로젝트 생성 안내 같은 평범한 문장에 걸렸다. 공격 근거가 다른 곳에 있는 샘플에 우연히 걸린 것으로 보인다(추정).
- 정규식은 바꾸지 않았다. RUN_CMD·RUN_INIT는 두 묶음에 함께 걸리는 6개만 점수가 0.7 → 0.91로 바뀌고, 걸림 여부는 바뀌지 않는다.

**한계**:

- 발췌는 지시 관련 단어가 많은 문장 5개뿐이라, 다른 곳에 있는 공격을 놓쳤을 수 있다. 그 경우 unclear가 과대 추정된다.
- SRC006·013은 실행해 봐야 드러나는 유형(출력 조작)이 많다(메타데이터 `evidence_type` runtime/constructed).

## 6. v1 AST를 만들지 않은 이유

계획(README §6)은 DECODE_EXEC·PIPE_TO_SHELL에 AST를 붙여 줄을 넘는 경우를 잡는 것이었다. 만들기 전에, 코드 블록 하나 안에서 줄을 넘는 결합을 정규식으로 넉넉하게 세어 AST로 더 잡을 수 있는 몫의 상한을 쟀다.

| 결합 (코드 블록 하나 안, 줄 무관) | 악성 | 정상 | v1이 놓친 악성 |
|---|---:|---:|---:|
| base64 디코드 + exec/eval/`\| sh`/subprocess/os.system | 42 | 0 | 6 (모두 SRC001) |
| 내려받기(curl/wget/requests.get 등) + exec/eval | 9 | 0 | 0 |
| 줄 이음 `\`로 넘어간 `curl … \| sh` | 0 | 0 | 0 |

상한이 6개(재현율 +0.1%p)라 tree-sitter-bash 의존성을 더할 만큼의 이득이 없다. 코드 블록 규칙은 v0에서도 기존 도구와 겹치는 샘플만 잡았다(new_vs_baselines 0).

## 7. 동결 규칙 목록과 판정 방식

규칙 17개(`31333de`): RUN_CMD, RUN_INIT, PROMPT_LEAK, OVERRIDE, LURE, HOMOGLYPH, RECON_DUMP, HIDDEN_DIRECTIVE, PERSONA_LOCK, CONCEAL(결합 전용), DESC_BYPASS(결합 전용), PIPE_TO_SHELL, DECODE_EXEC, REMOTE_EXEC, CRED_PATH(예외 있음), EXFIL_SEND, PERSISTENCE.

- **걸림 기준은 score > 0**이고 그대로 유지한다(2026-10-12 결정). 발동한 규칙이 하나라도 있으면 걸림이다. 결합 전용 규칙(CONCEAL, DESC_BYPASS)은 짝이 함께 걸려야 발동한다. 가중치가 쌓여야 걸리는 구조가 아니다. 가중치(CRITICAL 0.9, HIGH 0.7, MEDIUM 0.4, LOW 0.2)는 PR-AUC용 점수에만 쓰인다.
- 유지 근거: dev 오탐률 13/1,690 = 0.008로 기준(2%) 안이다. 더 높은 문턱(예: 0.8, HIGH 둘 이상)을 두면 재현율이 떨어지고, 문턱을 고를 근거가 dev 설계 데이터밖에 없다.
- 공통 동결(이번 주말 저녁, 시간은 세훈 님 공지) 뒤 test는 세훈 님이 1회 돌린다. test 결과를 보고 규칙·문턱·집계를 바꾸지 않는다.
- 재현율은 "전체"와 "script-only 제외" 두 가지로 보고한다. script-only 기준은 §8 초안을 세훈 님과 확정한 뒤 적용한다.

## 8. script-only 기준 초안 (11-05 공지 3번)

### 8.1 철회한 것

11-04에 "패키지에 SKILL.md 말고 코드 파일이 하나라도 있으면 스크립트형"으로 정하고 decisions.md에 적었다. 이 기준은 다음 문제가 있어서 **철회했다**.
- 공지의 "단순한 스크립트 호출만으로 제외하지 않는다"보다도 느슨하다. 코드가 있기만 하면 제외한다.
- dev 악성의 67%(4,490/6,658)가 빠지고, 그중에는 글에 공격이 있는 샘플이 많다. E4 글 공격 37개 중 9개가 같이 빠진다.

이때 낸 "스크립트형 제외 재현율 0.519"도 쓰지 않는다.

### 8.2 제안하는 절차

탐지기 결과는 어느 단계에서도 쓰지 않는다.

1. **필요조건(자동)**: 패키지에 SKILL.md 말고 코드 파일(확장자 `.py .sh .js .ts .ps1 .bat .rb .pl .php .go .lua .pyc` 등 또는 첫 줄 `#!`)이 있다. 없으면 script-only가 아니다.
2. **코드 근거 표시(자동, `data/script_only.py`)**: 동봉 코드에서 아래 동작을 찾아 `파일:줄:동작`으로 남긴다. 사람이 판정할 때 보는 자료일 뿐, 이것만으로 분류하지 않는다.
   - DL_EXEC(내려받아 실행)
   - OBF_EXEC(디코드 후 실행)
   - SECRET_READ(자격증명 경로)
   - ENV_DUMP(환경변수 통째로)
   - EXFIL_ENDPOINT(웹훅·텔레그램·공인 IP 등)
   - PERSIST(지속성)
3. **사람 판정**: SKILL.md 본문과 동봉 코드를 함께 보고 셋 중 하나로 정한다. 근거(본문 줄 또는 `파일:줄`)를 남긴다.

| 판정 | 기준 |
|---|---|
| text_attack | 본문에 사용자 몰래 에이전트의 목표·출력·권한을 바꾸거나, 정보를 빼내거나, 출처를 알 수 없는 코드 실행을 유도하는 지시가 있음(E4 기준표). 스크립트를 실행하라고만 하는 것은 해당하지 않음 |
| script_only | 본문에는 그런 지시가 없고, 동봉 코드에 구체적인 공격 동작이 있음(파일·줄로 제시할 수 있어야 함) |
| unclear | 둘 다 확인 못 함, 또는 코드 동작이 정상 용도와 구분되지 않음 |

4. **범위와 표본**(11-07 정함): 판정 대상은 1번 필요조건을 채우는 악성 전부다(탐지기 결과와 무관). 전수 판정 대신 출처별 층화 무작위 표본을 판정한다. test 100개(본 추정), dev 30개(절차 점검, 참고값), seed 0. 층 규칙: 대상이 100개 이상인 출처는 단독 층, 나머지는 "기타" 한 층. 비례 배분(최대 나머지), 층당 최소 2. `data/script_only_sample.py`.
5. **보고**: 제외 재현율 = (H − K₁) / (N − K). K는 후보 중 script_only 수, K₁은 그중 걸린 수이고, 층 × 걸림 칸마다 조사하지 않은 후보 몫을 Beta-Binomial로 뽑는 유한모집단 베이즈로 추정한다. 대표값은 중앙값, 범위는 95% 베이즈 구간(10,000회, seed 0). 사전분포 a=0.5가 주 결과이고 a=1을 함께 낸다. 전체 재현율이 기본 성적이고 이 값은 표본으로 추정한 보조 성적이다(11-10 개정, 11-07판은 층화 bootstrap. [script_only_proposal](../script_only_proposal.md) §2.4). unclear는 분모에 남기고 건수를 따로 적는다. 판정이 끝난 뒤에만 탐지기 결과를 붙인다. 세 탐지기가 같은 시트, 같은 식(`data/script_only_est.py`)을 쓴다. 제외는 집계 단계에서만 하고 데이터에서 빼지 않는다.
6. **일치도**: dev 10개, test 20개를 두 번째 판정자가 따로 판정하고 일치 건수를 적는다. 합의가 안 되면 unclear로 둔다.

### 8.4 정한 것 (2026-11-07, 왕민 결정, 세훈 님께 통보)

세훈 님과 정하기로 했던 항목을 동결 일정 때문에 왕민이 먼저 정하고 통보했다. 반대 의견은 동결 전까지 받는다. 상세와 근거: [script_only_proposal](../script_only_proposal.md).

1. **범위: (가) 필요조건을 채우는 악성 전부.** (나) "세 탐지기가 모두 놓친 것만"은 미탐이 대상을 고르게 되고, 걸린 쪽의 script_only(S_hit)를 분모에서 빼지 않아 제외 재현율이 항상 (가) 이상으로 나와서 쓰지 않는다.
2. **방식: 층화 표본 + 추정**(§8.2 4·5번). 전수 판정은 dev에서만 4,490건이라 하지 않았다. 에이전트 1차 판정은 악성 코드를 대량으로 읽어야 해서(안전 필터에 한 번 막힘) 하지 않았다.
3. **판정자: 왕민.** 원문은 `data/script_only_view.py`로 담당자 터미널에서만 본다. 교차 판정은 세훈 님이 한다(11-09 확정).
4. **시점**: 기준 문구는 동결 때 것으로 고정한다. dev 파일럿은 동결 뒤 test 판정 전에 하고, 절차 점검용이라 문구를 바꾸지 않는다(고칠 점은 기록만). test 표본은 동결 뒤 같은 스크립트·seed·n으로 뽑아 판정한다.
5. 근거가 약한 script_only 처리: ASB04_002011은 unclear로 돌렸고(§5.2), E4 7개는 코드 근거를 확인해 유지했다(§8.3).
6. §8.3의 90개는 미탐 표본이라 추정에 쓰지 않는다.
